# Reproducibility protocol (A5)

Status: proposed by the scientific-rigor program, workstream A5. Tools live in `repro/` (stdlib only, read-only):
`manifest.py` (build), `reproduce.py` (verify + compare), `cpu_replay.py` (cheap blind replay), `lint_science.py`
(registry consistency), `test_repro.py` (selftests). Claims C180-C189 and side quests SQ140-SQ149 are *proposed*
in `repro/proposed-claims.md` and `repro/proposed-side-quests.md`; nothing here edits the shared ledgers.

## 1. What a manifest is

One JSON file per finished run, `repro/manifests/<run>.json`, generated by `repro/manifest.py` from `meta.json`,
`summary.json`, git, the dataset folder, the venv and the checkpoint. **Never typed.** It is immutable (the tool refuses
to overwrite; `manifest_sha256` is the hash of everything else, and `reproduce.py` re-checks it).

| Field group | Content | Source |
|---|---|---|
| `code` | commit, describe, dirty flags, per-file sha256 of `gogeta/**/*.py` **at the commit**, combined hash, git tree SHAs | `git show` / `ls-tree` (nothing checked out) |
| `config` | config file sha256 at the commit; **effective config** (config + CLI overrides + arch + compile) and its sha256 | `meta/summary.json`, git |
| `seed`, `precision`, `deterministic_mode` | seed; autocast dtype and TF32 flag; whether `use_deterministic_algorithms` / `cudnn.deterministic` are on | static scan of `gogeta/train.py` at the commit |
| `dataset` | sha256 of every file in the dataset folder, split `sha256_16` from its `meta.json`, mtimes vs run start | streamed hashing, cached in `$GOGETA_DATA/repro-hash-cache.json` |
| `environment` | `recorded_at_run_time` (torch, CUDA, driver, GPU, python, pip-freeze hash) and `at_manifest_time` (same, measured now) | run-time block comes only from `meta.json["env"]` |
| `artifacts` | sha256 of checkpoint, summary, meta, samples, train log | files |
| `metrics`, `launch` | the run's own metrics; the exact launch argv | `summary.json`; derived |

**Back-filled manifests** (all 12 finished runs as of v0.4.29) cannot know the run-time environment: `gogeta/tracking.py`
did not record torch/CUDA/driver/GPU/pip-freeze. Those fields are the literal string `unknown (not recorded at run
time)`; the `at_manifest_time` block is labelled as such and is *evidence, not proof* that nothing changed. Code is
exactly recoverable for a run iff the commit exists and `code_dirty` was false at start (all 12 qualify). Going forward
the manifest is written by the run itself (patch `notes/patches/repro-manifest-at-run-end.patch`), which fills the
run-time block.

## 2. Determinism: what is and is not deterministic here

Seeds cover model init, the data sampler (`torch.Generator`, CPU) and the loop-count RNG. Step 0 therefore reproduces
exactly (C91 replay: 9.0900 both times). Everything after it runs on a GPU with floating-point reductions whose order
is not fixed. **Inventory (expected sources; the determinism experiment SQ140 measures which actually bite):**

| Source | Why it can differ run to run | Controlled by |
|---|---|---|
| fla Triton kernels (chunk GDN fwd/bwd) | Triton `autotune` can pick different block configs run to run, changing reduction order; some backward kernels accumulate with atomics (to be confirmed per fla version) | not covered by `torch.use_deterministic_algorithms`; pin fla autotune cache / configs |
| SDPA backward (flash / mem-efficient) | dQ accumulation uses atomic adds in the fast backward kernels | `torch.use_deterministic_algorithms(True)` selects a deterministic path or raises; or force the math backend |
| `torch.compile` / Inductor | fusion and Triton autotune choices differ per cache state; fused reductions change summation order | fixed `TORCHINDUCTOR_CACHE_DIR`, no `max-autotune`, or run uncompiled |
| cuBLAS matmuls (TF32 on) | split-K / workspace choices; TF32 rounding | `CUBLAS_WORKSPACE_CONFIG=:4096:8`; TF32 is a *numerics* choice, deterministic once fixed |
| index-add / scatter-add style backward (embedding-like ops) | atomic float adds | `use_deterministic_algorithms(True)` |
| Hardware / driver / kernel versions | different SASS, different libraries | environment block in the manifest |
| Data order, init, sampler, loop RNG | none: seeded | seed |

`gogeta/train.py` at every recorded commit sets **none** of these switches (`deterministic_mode.enabled = false` in
every manifest, from the static scan).

**Existing evidence.** C91: a 101-step GPU replay of E0 matched the v0.3.0 log at step 0 (9.0900) and read **2.8370 vs
2.8460 at step 100** (|d| = 0.009 on a single-batch training loss). Consistent with ordinary GPU nondeterminism
amplified over 100 steps, but not proven (code differed between the two runs by the `hf_llama` branch). SQ140 below
decides it by running the *same* code twice.

## 3. Two reproducibility levels

* **Bitwise reproduction**: same manifest, same seed, same precision, deterministic mode on -> identical checkpoint
  sha256 and identical metrics. Required only for runs claiming bitwise status (none today; SQ140 tests whether it is
  reachable on this hardware at all).
* **Statistical reproduction** (the default for every claim): a new run built from the manifest (same code hash, config
  hash, data hashes, seed) lands within the pre-registered tolerances below. A *different seed* is a **replication**, not a
  reproduction: it is judged against the seed sd, not these tolerances (see K7 replication protocol in `PREDICTIONS.md`).

`reproduce.py <manifest> --compare <new_run>` applies this table. It is the single source of truth; edit the block
(and cut a version) to change a tolerance, never the code.

```json tolerances
{
  "version": 1,
  "status": "provisional: seed sd not yet measured (Phase 2b / A2). Replace seed_sd_val_loss with the measured value and bump version.",
  "seed_sd_val_loss": null,
  "val_loss_sd_multiplier": 2.0,
  "val_loss_abs_floor": 0.004,
  "exact": ["steps", "tokens", "flops", "params_total", "params_non_embedding", "flops_per_token_default"],
  "exact_rel": 1e-9,
  "informational": ["wall_min", "tokens_per_s", "peak_mem_gb"],
  "informational_rel": 0.25,
  "early_train_loss": {"step": 100, "abs": 0.02}
}
```

Reading the block:

* **`val_loss` (and every `val_loss_r*`)**: reproduced iff `|new - old| <= max(0.004, 2 x seed_sd)`. 0.004 is provisional
  and *not derived from data*; it is roughly 0.7% of E0's 0.606 and smaller than the 3.6% E1-vs-E0 effect. Once Phase 2b
  measures the seed sd, set `seed_sd_val_loss`; the rule then uses whichever is larger.
* **`val_bits_per_char`** follows val_loss (the same relative tolerance, chars/token 3.72).
* **Exact**: step count, tokens, params and analytic FLOPs are arithmetic, so any difference means a different recipe.
* **Informational only**: wall time, tokens/s and peak memory depend on the machine and thermal state; reported, never
  fail a reproduction. A drift beyond 25% is flagged for a human, not a verdict.
* **Early replay** (`--new-log`): single-batch train loss at step 100 within 0.02. Provisional and derived from one
  observation (C91's 0.009), so treat it as a smoke test, not evidence of equivalence.
* Verdicts: `BITWISE`, `STATISTICAL`, `NOT REPRODUCED`, `NOT COMPARABLE` (effective config hash differs, so the new run
  is a different recipe and cannot be a reproduction).

Pre-registration of this block: it is committed before any run is compared against it. Changing a tolerance after
seeing a comparison is a protocol violation; do it in a separate version with the reason in the devlog.

## 4. Planned GPU experiment SQ140: same seed twice, with and without deterministic algorithms

Proposed queue item in `repro/proposed-queue.json` (waits for the `--deterministic` patch to be applied and a tagged
version; GPU, ~25 min). Prediction is registered in `repro/proposed-predictions.md`.

* Arms, each run **twice with the identical command** (seed 0, 10M tokens, otherwise the registered config):
  E0 default | E0 `--deterministic` | E1 default | E1 `--deterministic`. (E0 has no fla kernels, E1 does: the contrast
  attributes any residual nondeterminism to the fla/Triton kernels.) `--deterministic` = `CUBLAS_WORKSPACE_CONFIG=:4096:8`
  + `torch.use_deterministic_algorithms(True, warn_only=True)` + `cudnn.deterministic`; warnings are logged, not hidden.
* Measure per pair: step-0 loss, loss at steps 10/50/100/…, final val loss, checkpoint sha256, number of differing
  weight tensors and max |delta|; also one pair with `--compile` off to isolate Inductor.
* Decision rules (fixed now): bitwise reproduction is "reachable" for a config iff both runs give equal checkpoint
  sha256 with `--deterministic`. The statistical tolerance is "consistent" iff every default-mode pair has
  |d val_loss| <= 0.004; otherwise 0.004 is too tight and must be raised before any reproduce verdict is trusted.
  The same-seed spread is a **lower bound** for the seed sd (different seeds also change init and data order).

## 5. Blind independent replication checklist

Goal: a person (or agent) who has *only* the repo, the manifests and the data-prep recipe reproduces the headline
E0 / E1 numbers, without reading devlog narrative, without access to the original `$GOGETA_DATA`, and without being
told the expected values (the checker compares afterwards). "Blind" = the replicator does not choose tolerances, seeds
or "which run counts"; they are read from `repro/manifests/` and this document.

Preparation (by the original team, once per release): tag the version; commit manifests; publish
`repro/manifests/*.json`; hold the expected metrics out of the replicator's instructions (the manifest contains them,
so the replicator is told to run `reproduce.py` only *after* writing their own result file).

Checklist (replicator):

1. [ ] Fresh clone: `git clone <repo> && cd Gogeta-0 && git checkout <manifest.code.commit>` (or the tag). Do not copy any `$GOGETA_DATA`.
2. [ ] Fresh environment: new venv from the lock files (`requirements.txt`, then torch from the CUDA index per its header). Record `pip freeze | sha256sum`; compare with the manifest's `at_manifest_time.pip_freeze_sha256` and report the differences (torch/CUDA/driver/GPU). Differences are *reported*, not hidden.
3. [ ] Rebuild the data: `python tools/prepare_data.py ...` as in the dataset card; then `python3 repro/reproduce.py <manifest>` must show `MATCH` for `data train.bin`, `val.bin`, `tokenizer.json`, `meta.json`. If any is `MISMATCH`, stop: the data differs and no downstream number is comparable (report which file).
4. [ ] Code and config: the same command shows `MATCH` for code and config (a fresh clone at the commit guarantees it).
5. [ ] **Cheap tier (CPU, minutes, no GPU):** `python3 repro/cpu_replay.py <manifest> --steps 1` reproduces the step-0 training loss of the manifest's log within 0.02 (fp32 CPU vs bf16 GPU; this validates init, data order and seed handling end to end from the manifest alone). Mark the result `CPU-STEP0`.
6. [ ] **Mid tier (GPU, ~3 min + compile):** launch the manifest's command with `--max-tokens 3276800` (100 steps); `reproduce.py --compare` is not applicable (different recipe) so use `--new-log` against the original log: step-100 train loss within 0.02 (provisional). Mark `GPU-STEP100`.
7. [ ] **Full tier (GPU, ~25 min E0, ~40 min E1):** launch the exact command of the manifest, wait, then `python3 repro/reproduce.py <manifest> --compare <new_run>`. Record the verdict (`BITWISE` / `STATISTICAL` / `NOT REPRODUCED`). For E1 add `--lr` per the manifest (E1's headline run used the untuned 3e-3).
8. [ ] Write `replication-<replicator>.json` with: replicator id, date, clone commit, pip-freeze hash, GPU/driver, every `reproduce.py` verdict, and the new run's manifest. Commit it under `repro/replications/` *before* reading any expected value in the devlog.
9. [ ] Report negative results exactly like positive ones (`NOT REPRODUCED` is a result). The original team may not edit tolerances afterwards without a new version.
10. [ ] Independence audit: list what the replicator was *not* given (original data folder, logs, checkpoints, the devlog interpretation).

Headline runs and their manifests: E0 `repro/manifests/E0-20261122-122059-s0.json`, E1 `repro/manifests/E1-20261122-124440-s0.json`
(E2 `E2-20261122-132340-s0.json` for the loop results). The K7 20M-token LR-sweep runs have manifests too.

## 6. Known limits

* Back-filled manifests cannot prove the run-time torch / CUDA / driver. A strict replication of those runs is therefore
  *statistical on a possibly different stack*; the first manifests written by the run itself (after the patch) close this.
* Dataset hashes were computed on the current files; mtimes older than the run start support, but do not prove, that
  they are the files the run read. `meta.json`'s `sha256_16` split hashes are the dataset builder's own record.
* The log is hashed as it is at manifest time; logs are append-only, so a later append changes its hash. Prefer the
  checkpoint and `summary.json` hashes as identity.
* 12 runs are covered; the E9 first attempt, the in-flight campaign runs and smoke runs have no `summary.json` with
  status `done` and are intentionally skipped.
