## 2. Critique

**2.1 "Linear time" is an analytic claim, not a measured one.** model.py implements SWA with a dense T x T boolean mask (code-read, `Attention._mask`), so the kernel is O(n^2) at every length. `flops_per_token` credits SWA with min(window, T/2) keys (code-read). The per-FLOP figures (E1 "0.94x", E1's cost advantage) therefore use the analytic count, while measured wall time says GDN is 1.62x dense and 8% worse at equal wall-clock (quoted, SQ338). Efficiency wording should say "analytic FLOPs" unless it sits next to a measured time.

**2.2 The FLOP counter overstates truncated-BPTT arms (code-read, check before use).** `flops_per_token` multiplies every loop pass by 3 (forward plus backward), but `forward` runs the first `r - bptt_loops` passes under `torch.no_grad()` (code-read, model.py lines 356-359), which costs about 1x forward. E27 (truncated) and A2s both report FLOPs through one counter. Confirm that the 3.41-3.43e16 vs 3.79e16 figures in a2_runs.json were not computed from this function. If they were, the 10% compute gap behind C209 is off, and the "compute-matched" sign of the 17% headline could change.

**2.3 The long-context pillar has no positional control.** SQ351 (quoted, DEVLOG v0.5.11: GDN hybrid -60.7% vs dense beyond 1,024 tokens) compares a dense RoPE model trained at 1,024 with a hybrid whose attention is mostly SWA-256. Two explanations fit the same numbers, and the run does not separate them: (a) dense attention sees relative distances never trained, which is classic RoPE out-of-range degradation; (b) the hybrid never attends beyond 256 tokens, so it is shielded from that failure rather than extrapolating well. The "first measured evidence for the linear-time pillar" needs a dense arm with a standard positional fix (position interpolation or a NoPE layer, which SQ52 and SQ237 only partly cover). Until then, read the -60.7% as "against unscaled RoPE".

**2.4 The main 200M contrasts are compute-unmatched and LR-unbracketed.** C209 says the 17% gap is A2s vs E27 with E27 on about 10% less compute, so the headline is not compute-matched. C202's cell LRs were chosen at 20M and reused at 200M; the H2' check shows 2e-3 worse by +0.2 to +0.9% at 200M, which is smaller than the +6.2% interaction, so LR alone probably does not explain it (computed from quoted numbers). C200 (dedup, +1.6%) was tuned on v1 and used unchanged on v2, which biases against the new arm (quoted, C200 limitations). Each of these is labelled, but the README's bold bullet "The fusion does not stack at 200M" is still stated as fact.

**2.5 The "clean" set is still in-distribution.** clean80 keeps documents with up to 80% of their 13-grams seen in training (README glossary). Every assembly result (A1-A3) is measured on code-py-v2 validation from the same source family. The only out-of-corpus test, SQ99 / C192, was refuted on the pooled registered criterion (quoted). SQ379 (A2 out of corpus) is an idea, so every "recipe" claim is untested outside the distribution it was tuned on. This is the largest validity gap for the goal-6 story.

**2.6 Small-N method.** The A1 screen tested about ten arms on two seeds and picked winners, and fresh seeds confirmed them (quoted). That is sound, but the screen's -8.3% is selection-inflated; the fresh -7.56% is the number to use. Three-seed paired t intervals (t = 4.30, df 2) are wide in principle, and the reported widths depend on a seed sd that is itself estimated from three values (the 13:40 review's I2 covers this, so I do not repeat it).

**2.7 Ternary is simulated.** BitLinear fake-quantises with per-tensor absmean weights and per-token int8 activations (code-read). The "1.58 bits" memory figures (A3mx 44.0 MB) assume ideal packing that has not been built or measured (SQ378 is pending). The +9.5% ternary cost is a simulated-kernel cost, so claims about inference cost of ternary should say so.

**2.8 Reading the README.** The headline metric is "quality per bit of weight memory and per FLOP" (DEVLOG high-level goals, quoted). Most ledger claims use per-FLOP or per-parameter framing, and no run matches weight bits. Ternary's case is therefore decided on a metric the project never tests directly (see idea 3).

## 3. Alternative ideas (all (spec))

Each idea is checked against side-quests.md and QUEUE.md by search. Items marked "partial" overlap with a queued item and say how.

**I-a. Mixture-of-Depths routing inside the loop (novel to our queue).** Hypothesis: a learned top-k token router that skips the core for about half the tokens on each pass matches the full loop at about half the core FLOPs, which turns C6's loss-per-FLOP deficit into a tie. Cheapest test: E2 layout at 20M tokens, capacity 0.5 per pass, against E9 (unlooped) and full-loop E2 at matched FLOPs, one seed, GPU about 10 min. Result that changes plans: beating E9 by more than 1% at matched FLOPs revives loops as a compute lever; tying E9 means loops are only a unique-parameter lever (D3 settles that way). Novelty: refs/README.md lists Mixture-of-Recursions (per-token adaptive depth), but no side-quest or queue item tests token routing across passes; SQ92 is only the oracle upper bound.

**I-b. Positional control for the long-context pillar (partial: SQ237, SQ294).** Hypothesis: most of the dense model's +160% degradation past 1,024 tokens (quoted, SQ351) is RoPE out-of-range, and linear position interpolation (scale 1/4) on the existing dense checkpoints removes more than half of it. Cheapest test: eval-only, no training, on the 3-seed SQ351 checkpoints (cells 000 and 100) with and without interpolation, 153 long files, GPU about 5 min or CPU about 20 min. Result that changes plans: if interpolation closes more than half the gap, the -60.7% is a positional artifact and the pillar statement is restated. Novelty: SQ237 trains or evaluates GDN-only models; it does not evaluate the dense arm with a positional fix.

**I-c. Bits-matched quality (partial: SQ371).** Hypothesis: at equal weight bits (the README's headline metric), a ternary model about 3x wider than an fp16 model of the same memory beats it on clean80. Cheapest test: 20M tokens, two arms at matched weight bytes (ternary wide vs fp16 narrow, from the existing E24 and A2 shapes), seeds 0-1, GPU about 10 min. Result that changes plans: a clear win supports ternary on the project's own metric; a tie or loss means ternary is justified only by kernel speed, which is unmeasured. Novelty: SQ371 is a computed memory table, not a quality run.

**I-d. Sparse top-k retrieval in the coda for copy-at-distance (partial: SQ383).** Hypothesis: one top-k retrieval attention layer (k = 16 keys chosen by score) outside the loop matches full coda attention on the SQ347 copy probe at gaps 128-512, at O(n k) cost. Cheapest test: 20M tokens with the coda swapped, copy probe at three gaps, GPU about 10 min. Result that changes plans: matching full attention keeps the "nothing quadratic inside the loop" rule and a coda that is linear at inference; failing it means SQ383's full-attention fix is the only option. Novelty: SQ383 asks whether full coda attention carries copy; this asks whether a sparse version can.

**I-e. Self-distillation from the full-precision teacher to close the ternary gap (spec; check the side-quest list before registering).** Hypothesis: logit distillation from the full-precision model of the same shape recovers part of the ternary cost (A2s vs A2f, +9.5%) without changing the architecture. Cheapest test: 20M tokens, ternary core student with and without a KL term to a full-precision teacher, two seeds, GPU about 10 min. Result that changes plans: recovering more than a third of the gap means the ternary cost is a training-recipe cost, not a capacity cost. Novelty: not found in the side-quest or queue search above; this is a recipe change, not a new mixer.
