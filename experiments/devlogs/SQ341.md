# SQ341: loop-count curve on the 200M F2 loop cells

**Status:** done (descriptive, not registered) · **Verdict:** both loop cells are best at r = 4 (the default) and get monotonically worse with more passes (+5.6% at r = 12 for 010, +4.3% for 111, vs r = 4); fewer passes also hurt (r = 1: +8.3% / +7.3%). The curve is a property of the trained model, not evidence that looping adds depth-compute · **Links:** script `experiments/checks/sq341_sq348_loops.py` (shared with SQ348), results `experiments/checks/results/sq341.json` (raw: `sq341_sq348_raw.json`), CPU path `sq339_cpu.py`

## Method
Cells 010 (E22: prelude 1 attn, core 3 attn x r, coda 1 attn) and 111 (E27: ternary, prelude swa, core gdn,gdn,swa x r, coda attn), best-LR runs (6e-3), seeds 0-2, trained with r ~ U{1..7}. The trunk is run once with 12 passes and the state after every pass k is read out through coda, norm_out and the head, which equals evaluating with loops = k (checked against `model(x, loops=k)` for k = 1, 4, 12 on 12 docs: max per-doc |dNLL| = 0.0 nats for both cells). Metric: aggregate bits/char on the fixed 300-doc clean80 subset (the same docs as SQ339), fp32 CPU, window 1024. The CPU path agrees with the GPU clean80 number to 0.015% (SQ339 devlog). git 36acccc/58a9ba8 working tree.

## Reading and caveats
- The penalty of the loop cells vs dense (+9.6% at 010, +29.6% at 111, on this subset) is flat for r in 3..5 and not an artifact of the default r: no r closes it, and r beyond the trained range (8-12) degrades smoothly, with no cliff at 7.
- r = 3 is within 0.06-0.2% of r = 4: the core's marginal pass gains almost nothing beyond r = 3.
- 300 docs; descriptive; n = 3 seeds, sd across seeds is small relative to the r-effects but df = 2.
