## 2. Critique

**2.1 MoE capacity confound (C206, C208). Strongest issue (computed + quoted).** C203 says that on the E1 stack a dense SwiGLU with the same total params (2048 hidden) beats the top-2 MoE (4 experts x 512) by a further 1.6%. The A2s MoE in C206 is the same kind of bank in the core. Its expert hidden total is 4 x 512 = 2048 against the dense FFN's 1024, so it has about 2x the core FFN params (computed from the C206 scope). The -3.3% is therefore measured against a parameter-smaller dense FFN. I found no assembled-stack arm with a dense 2048-hidden FFN in the status view (I grepped claims-status.md; check the registry before trusting this). Prediction (spec): that arm ties or beats the MoE, and C206 becomes a capacity result.

**2.2 Ternary "compute" is not in the FLOP count (code-read).** `flops_per_token` (model.py) has no ternary term: BitLinear counts as full-precision FLOPs. So every ternary arm is "matched compute" at full-precision cost, and the only measured ternary benefit is weight bytes (C9, computed). Any "ternary costs X% at matched compute" sentence is a quality-at-equal-FLOPs statement. It says nothing about speed. D2 should say this in its wording.

**2.3 Matched FLOPs, not matched params, for most headlines (quoted + spec).** C197 showed that unique params beat loops at matched FLOPs. Yet C206, C209 and C212 are all matched on FLOPs, and parameter counts differ between arms. Unless a param-matched arm is in the registry, the default reading of these headlines is "more params", not "this mechanism". The 14:41 review's 2.1 covers the FLOP side only.

**2.4 Init depth may not match the depth actually trained (code-read; magnitude unknown).** `_init_weights` scales residual-output init with `effective_depth()`, which defaults to `cfg.loops` (model.py, `effective_depth`). Training samples r from U{loops_min..loops_max}, so for a loop arm the init may be scaled for a depth that is not the one run. SQ326 tests flat vs scaled init, but I did not see it test this mismatch. Check the A2/A3 configs: does `cfg.loops` equal the fixed r used in the arm?

**2.5 Thin seed inference on the headline (quoted).** The CI in C209 is a paired t interval on 3 seeds (df 2). It gives a narrow interval only because the three seeds agree closely. It is one horizon (200M), one corpus, one LR-bracketed arm. The horizon is already tested (SQ398, C201 vs C202 sign flip), so I would not repeat it. A seed-level table with the raw per-seed numbers should go into the devlog next to the CI.

**2.6 Eval loop count is not reported per arm (code-read).** `forward` defaults to `cfg.loops` at eval. For loop arms the eval r is not stated in the claims I read. Two arms can be compared at different r without anyone noticing. The fix is cheap: record eval r in every result JSON.

## 3. Alternative ideas (each checked against side-quests.md and QUEUE.md)

**I-1. Memory-matched ternary control (new; D2 is FLOP/param-matched).** Hypothesis (spec): at equal stored bytes (ternary weights plus tied FP embedding, counted), a full-precision model with about one-tenth the unique params beats the ternary A2s. Cheapest test: 20M tokens, A2s vs an FP model sized to the same bytes, 2 seeds, about 15 GPU-min. Change of plan: if the FP-small arm wins, the memory case for ternary (goal 6, 24 GB target) needs a speed argument, which we cannot yet measure. Novelty: D2's listed items (SQ339, 355, 365, 369, 371) compare at matched params; I found no bytes-matched arm.

**I-2. Dense 2048-hidden FFN inside the assembled core (capacity control for C206/C208).** Hypothesis (spec): the dense-2048 arm matches or beats A3m, so the MoE step is capacity, not routing. Cheapest test: 20M tokens, A2s with the core FFN at hidden 2048, 3 seeds, about 20 GPU-min; if the 20M result holds, confirm at 200M later. Change of plan: if dense ties or wins, C206 and the "MoE core" step in A3mx lose their routing claim, and the A3mx-vs-E24 gap should be re-read against capacity. Novelty: C203 (E1 stack) has this control; the assembled stack does not, as far as I found. Extends C203 rather than repeating it.

**I-3. GDN beta ablation: is the delta rule doing the work? (new).** Hypothesis (spec): most of GDN's gain over SWA on code is the decay gate and gating, not the learned write strength beta. Cheapest test: E1-stack at 20M, 2 seeds, three arms: learned beta, beta fixed at 1, beta fixed at 0.5 (one-line change in `GatedDeltaNet.forward`); about 10 GPU-min. Change of plan: if fixed beta ties learned beta, the mixer case should be argued as gated linear attention. That weakens the state-tracking motivation (C43, C18) and feeds Q23's loop decision. Novelty: side-quests has no beta ablation (grep for "beta" hits only SQ70 and SQ222, which are about kernel arguments).

**I-4. Eval-time loop budget on the existing A2s checkpoints (new for A2s; SQ14/SQ92 are E2-only).** Hypothesis (spec): the headline recipe's second pass does little, so loss at r=1 is within about 1% of r=2 on clean80. Cheapest test: inference only on A2s seeds 2-4, r = 1, 2, 3, clean80, CPU or a few GPU-min; no training. Caveat: a model trained at r=2 evaluated at r=1 is a distribution shift, so a large gap shows the pass is used, not that it adds capacity beyond unshared depth. Change of plan: if r=1 is within 1%, the headline is a 6-block GDN-ternary stack with a redundant pass, and the loop claims in the assembly arc (C212, C208) need rewording. Novelty: not run on A2s as far as I found, and it costs no training.

**I-5. Init-depth audit against sampled r (new, part of 2.4).** Hypothesis (spec): for at least one registered loop arm, the init depth used by `_init_weights` differs from the r actually trained. Cheapest test: CPU, 5 min: for each arm config compare `effective_depth()` with the fixed or mean sampled r; print residual-init std ratios. If the ratio is above 10%, rerun the affected pair at 20M, 2 seeds. Change of plan: a mismatch means some loop comparisons carry an unregistered init confound. Novelty: SQ326 covers init schemes; this checks the depth input, not the scheme.
