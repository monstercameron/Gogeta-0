## 2. Critique

**2.1 A2 cannot yet say whether the components work together.** A2s changes four things relative to E27 at once: the core shape (6x2, the A1g parameter change), fixed r, contractive injection, and ternary in the core. P1 ("stacking works, sub-additively") therefore cannot be attributed to any one winner. A2f removes ternary only; no arm removes the shape, the fixed r or the injection. Since A1g is itself a parameter-changed arm, most of a predicted -17% would be the C197 effect the project already knows. The 1200 review's leave-one-out (its §2.7) was not adopted in the registration or in its triage.

**2.2 Power is too low for the decisions written.** Three seeds give df = 2. E27's per-seed sd is about 0.55% (the three values in PREDICTIONS; computed). A paired difference then has sd 0.78%, SE over three seeds 0.45%, and a 95% half-width of about 1.9% (t = 4.30; computed). P5 (adapters, -1%) cannot be decided at all. The "within 5% of dense" tolerance is wider than the project's own effects (C197 -7%, C203 -2.7%).

**2.3 The competitiveness bar uses a loose tolerance and an incomplete reference set.** The rule compares A2s with dense E20 at matched FLOPs, within 5%. E20 has more unique parameters (C202 scope: about 25M total for the family) than A2s (15.1M non-embedding), so a "pass" can be a C197-type win for dense. E24 (unshared GDN, FLOP-matched) is listed as a reference but is not in the competitive rule. The 1210 triage says "agreed" to report against an unshared E32-style reference too, but the A2 section of PREDICTIONS still lists only E20, E24 and E27.

**2.4 Seed hygiene is partial.** A2s is fresh (seeds 2-4). The reference seed 2 for E20, E24 and E27 comes from SQ263, the F2 seeds that C202 analysed (seeds 0-2). Those references are not fresh relative to C202; say so in the ledger row.

**2.5 Check a config before dispatch.** The staged A2 JSON files (a2s, a2f, a2a) set `"max_tokens": 20000000` (code-read), while their description and PREDICTIONS say 200M "via --max-tokens". Confirm the launch passes 200M and that the recorded run config shows it.

**2.6 Ternary has no measured payoff for goal 6.** Goal 6 targets a 24 GB card. A 1.2B model at 2 bytes per weight is about 2.4 GB of weights (computed); SQ289 exists to test whether VRAM binds, and the side-quest text already assumes it does not. C14 is WRONG FOR OUR CODE (no ternary speedup), and the ternary penalty is measured (C202 cell 001 at +15.8% at 200M; A1e in v0.5.4). So in the registered goals ternary buys nothing deployable until ternary kernels exist. (spec, my judgment:) E61 should say what ternary must buy, such as storage bits or a measured int8/ternary speed, or drop it. A2f vs A2s is the number that decides this, and the registration does not say what result would drop ternary.

**2.7 Efficiency is analytic at 1k context.** FLOPs are analytic; sliding-window layers are counted at window size but run as dense masks (C12); every quality number is at T = 1,024. "Competitive per FLOP" is the only axis A2 tests in its primary rule. The 1210 triage made throughput a flag, not a gate, so a winner that costs wall-clock can still be stacked silently.

**2.8 Byte track (E12-E16).**
- **E14's H-C2F control is confounded by unique parameters.** E14d (two unshared blocks) has twice the unique parameters of E14b (shared x2). C197 says unique parameters win at matched FLOPs, so the registered "sharing neither helps nor hurts (+-0.5%)" can be refuted by parameter count alone. The parameter-matched arm A'' (two half-width blocks) is in the analysis note's v0.4.66 correction but not in the registered E14 predictions (grep finds no A'' or half-width arm there).
- **E13 picks P at matched bytes, not matched FLOPs.** The DEVLOG v0.4.68 table gives 172M FLOPs per token for P = 2 and 95M for P = 4. "P = 2 best so far" is therefore the expected result at 1.8x compute and says nothing about "patching pays" (best arm at <= 0.5x E12's FLOPs).
- **The E13 LR is weakly estimated.** It came from one seed at 153 steps, and the curve is non-monotone (6e-3 at 2.967 is worse than 1.2e-2 at 2.869; DEVLOG v0.4.85). The LR effect (about 9% between 3e-3 and 6e-3) is larger than the 1-4% granularity effects the registration tests.
- **The note's recommended first test is not queued.** X1 (speller on frozen E1; SQ207, "top pick, accepted, high priority") is absent from queue.json and QUEUE.md (grep). It is the cheapest test of sharing with the global model fixed.
- **README wording vs AGENTS §0.** "P = 2 is best so far" is a result with no ledger row. It should be labelled exploratory or removed until a results block exists.

## 3. Alternative ideas (6 new; all (spec) hypotheses)

**N1. Is the 20M-to-200M reversal a schedule artifact?** Hypothesis: part of the C201 vs C202 sign flip comes from cosine annealing whose length scales with the horizon, not only from the ingredients. Cheapest test: cells 000 and 111, 2 seeds, 20M, WSD schedule (stable 80%, linear decay) vs the current cosine at the same LR; 8 runs, about 1 GPU-min each (from the F2 20M medians, computed). Plan change: if I under WSD at 20M is as positive as under cosine, C201's 20M synergy is schedule-independent. If I flips sign, every 20M screen of interactions is untrustworthy and the 200M gate becomes mandatory. Novelty: SQ324 and SQ337 read existing cosine curves; no schedule variant is queued.

**N2. Ternary code churn as a noise floor.** Hypothesis: late in training the fraction of ternary codes that flip per step does not fall to zero, so the final iterate is partly random and part of the ternary penalty is noise. Cheapest test: no training change; log per-step code flips (changes in round(W/scale)) on cells 001 and 111 at 20M, 1 seed, about 1 GPU-min extra. Plan change: if churn in the last 10% of steps exceeds about 1% of codes per step, add an EMA of the latent weights or a longer decay to ternary arms. If churn is near zero, the ternary penalty is structural. Novelty: SQ365 measures jitter at checkpoints, SQ217 is a plain weight EMA for LR robustness, and churn during training is not measured.

**N3. Do loops win on a state-tracking probe at 200M, even though they lose on loss?** Hypothesis: goal 2 rests on state tracking (K5, tiny models), but every 200M number is LM loss, where loops lose (C6, C42). Cell 010 may win a running-sum or variable-binding probe that its loss hides. Cheapest test: inference only on the 200M cells 010 and 000 (3 seeds each, on disk); a synthetic running-sum and binding battery at 1k context; about 10 CPU-min (guess). Plan change: if 010 beats 000 on the probe by more than the seed spread, goal 2 needs a task-specific eval in E61. If it ties or loses, goal 2 has no measured support at 200M. Novelty: K5 used tiny models; SQ68 is a Zoology MQAR harness for mixers; no probe runs on the 200M F2 checkpoints. Partial overlap with SQ68.

**N4. A goal-6 decision memo before more GPU money (CPU only).** Hypothesis: at 24 GB (21.5 GB usable, SQ289's assumption), neither ternary nor loops changes what fits, so their case rests on speed, which is unmeasured for both. Cheapest test: a computed table for 1.2B: weight bytes at bf16 vs ternary-core, state/KV bytes, and per-token decode cost at r = 1, 2, 4 from the verified fused-recurrent path (C111). About 5 CPU-min. Plan change: if neither ingredient changes what fits or the measured decode-second, E61 is planned unfused and the fusion becomes a gated side branch. Novelty: SQ289 measures VRAM and SQ362 measures the decode frontier on GPU; this memo is a decision on their numbers, partly overlapping.

**N5. Parameter-matched sharing inside the byte decoder.** Hypothesis: the H-C2F gap is unique parameters, not sharing (see 2.8). Cheapest test: X1 (SQ207) with arms A (1 pass), A' (2 unshared), B (shared x2, FLOP-matched to A'), and the parameter-matched A'' (two half-width blocks); frozen E1 features recomputed on a 20-50M-token subset (per the note's correction); 2 seeds; about 10-20 GPU-min per arm. Plan change: if B beats A'' at equal parameters, the shared loop has value and E14 keeps it. If A'' ties B, the byte loop is a parameter-saving device and E13/E14 should be read that way. Novelty: A'' is in the v0.4.66 note but not in PREDICTIONS or the queue.

**N6. A matched-FLOP reread of the granularity sweep.** Hypothesis: at matched FLOPs, P = 4 or 8 beats P = 2 (the registered E13 is matched bytes). Cheapest test: 20M bytes, 2 seeds, E13 arms at equal FLOPs (P = 2 with fewer global layers, or fewer decoder passes); about 6-8 GPU-min. Plan change: if the P ranking flips at matched FLOPs, the registered argmin rule must be replaced before the 200M sweep is read as a result. Novelty: the registered E13 is matched bytes; a matched-FLOP reread is not queued.

## 4. The one experiment I would run next

**The A2 leave-one-out ladder at 200M, on fresh seeds 5-9, registered after the A2 readout and before dispatch.** Arms, each paired with A2s by seed:
- A2s minus the contractive injection;
- A2s minus fixed r (random r in {1, 2}, bptt 2);
- A2s with the 6x2 shape replaced by a 3-block core x 4 passes: the same 12 block applications and the same mixer mix (8 GDN, 4 SWA), half the unique core parameters. This tests C197 inside the stack;
- A2f (ternary removed; already staged, rerun on seeds 5-9);
- A2s itself on seeds 5-9.

That is 25 runs of about 9 min each (the reviewer's estimate for a 200M run of this shape), about 3.8 box-hours, or about $2 at the rate implied by v0.5.1 ($4.4/h for eight boxes; computed). Money is not the constraint; registration is. Five fresh seeds give a 95% half-width near 1% (sd 0.78% per pair, SE 0.35%, t = 2.78 at df 4; computed).

Why this one: it attributes the A2 stack to its components, which the "do the components work together" question needs; the shape arm is the parameter-matched complement of A1g and tests C197 inside the stack; the ternary arm decides the goal-6 question in 2.6; and five fresh seeds have the power that three do not.

Pre-registration (spec): a component stays in E61 only if removing it costs at least 1% paired on the clean80 metric. Ternary additionally needs a measured speed or memory case to stay. Falsifier: removing the shape costs under 1%, which would mean the unique-parameter lever is absent from the assembled stack and the loop-to-unshared comparison is closed for this design.
