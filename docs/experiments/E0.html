What it means, in plain English

We built the "control group": a small, completely ordinary AI model that learns to write Python code. Every later experiment gets compared against this one.

It has about 14 million adjustable numbers (its parameters). It read 200 million chunks of Python, practising one skill over and over: guess what comes next. Then we tested it on code it had never seen.

How good is it? For each next chunk of code, it's on average about as unsure as if it were choosing between 1.8 equally likely options. Picking from 8,192 possible chunks, that's a very confident guesser. Put another way: if you used it as a compression program, it would shrink new Python code to about 3% of its size. The best everyday compressor (xz) gets the same code to 15%, and zip-style gzip to 25%.

Can it code? Sort of. Asked for a palindrome checker, it wrote a correct one, with correct tests. Asked for Fibonacci, it got stuck repeating else: over and over, a classic small-model failure. It has learned what Python looks like much better than how to think in it.

Prediction (written before the run)

Written 2026-11-22 before the run. After 200M tokens of Python (code-py-v1), full-val loss lands in 0.90-1.30 nats/token (about 0.35-0.50 bits/char). Throughput about 170k tok/s compiled, about 20 min. Samples are syntactically plausible Python with coherent short functions but frequent logic errors.

What we tested

The most standard design there is: 6 layers of full attention, the mechanism behind modern chatbots. In every layer, every word looks back at every earlier word. That's powerful, but its cost grows with the square of the text length, which is the cost FusionDance wants to get rid of.

Results

Breakdown of the findings

  1. Training was smooth. No sudden loss spikes; the "gradient norm" (how hard each update pushes) never went above 0.38 after warm-up. Nothing to debug.
  2. Final validation loss 0.606 (0.235 bits per character). That's far better than the 0.9–1.3 I predicted. The data turned out to be very regular: curated and partly machine-generated code with lots of repeated patterns (docstrings, assert lines, similar exercise formats). A low number here means "this dataset is predictable", not "this model is great at programming".
  3. Fast: about 210,000 tokens per second at steady state, 23 minutes in total, under 5 GB of GPU memory.
  4. Samples (text the model wrote from a prompt, temperature 0.8): - Write a python function to check whether a string is a palindrome. → a correct one-liner (s == s[::-1]) plus correct test asserts. - def fibonacci(n): → a few plausible lines, then dozens of repeated else: lines. It got stuck in a loop of its own making.

Caveats

  • One run (seed 0). Re-running with a different random seed would give a slightly different number; we don't yet know by how much. (The replication runs were interrupted; see the devlog.)
  • These losses only compare within this project. Different data and tokenizers give completely different numbers, so 0.606 can't be compared with published models.
  • Loss measures prediction, not correctness. A test that actually runs the model's code is on the to-do list.
