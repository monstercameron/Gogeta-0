# SQ376: goal-6 data gate from the Phase 2b in-training eval curves

**Status:** done (descriptive, not registered) · **Verdict:** the 14M E1 and E10 models are still improving steeply between 100M and 200M tokens: in-training val loss falls 22.0% (E1) and 19.9% (E10), every run, far above the 1% gate. The number is confounded by the cosine schedule (see caveat), so it shows "not data-saturated at 200M tokens" but does not size the data need of a longer run · **Links:** script `experiments/checks/sq376_data_gate.py`, results `experiments/checks/results/sq376.json`

## Method
From the launcher logs (`~/fusiondance-data/logs`, fleet copies) of finished 200M-token runs (6,104 steps x 32,768 tokens): the lines `eval step N: val/loss` (128 val sequences of 1,024 tokens, every 250 steps). Gain = 100 x (1 - L(last) / L(100M)), with L(100M) the eval at step 3000 (98.3M tokens) and L(last) the eval at step 6000 (196.6M tokens). Runs found in the first pass (launcher logs): E1 seeds 0-2 and E10 seeds 0-2 (n = 3 per arm); the 7-seed fleet group is in the update below. Data: code-py-v1 val (the training-time val set, not clean80), v1 train.

## Update 2026-11-23 (seven seeds, as the row specifies)
The first version only found three seeds because the 5090 fleet logs (`p2b-E1-s0..s6.log`, `p2b-E10-s0..s6.log`) carry no launcher header; the script (`sq376_data_gate.py`) now reads the run name from the `run:` line and the LR from the run's meta.json, and reports both groups. Phase 2b fleet runs (code-py-v1, 200M tokens, 6,104 steps), n = 7 seeds each:
- E1 (lr 6e-3): gain from 100M (step 3000) to the last eval (step 6000, 196.6M tokens) = **22.04%** (sd 0.29; per seed 21.73, 22.02, 22.01, 22.42, 21.84, 21.81, 22.44); val loss 0.7755 -> 0.6046.
- E10 (lr 3e-3): **20.09%** (sd 0.26; 19.56, 20.27, 20.10, 20.29, 19.98, 20.26, 20.18); val loss 0.7564 -> 0.6044.
- All 14 runs far above the 1% gate. Late slope: the last 17% of tokens (step 5000 -> 6000) still gives 5.3% (E1) and 4.4% (E10).
The earlier launcher-log group (seeds 0-2) agrees (22.0% and 19.9%). The cosine-schedule confound and the 128-sequence v1 val caveats above are unchanged. Result file now holds both groups under `groups` (keys `p2b_fleet/E1@0.006`, `p2b_fleet/E10@0.003`, `launcher/...`).

## Caveats (they matter for the decision)
- Each run's cosine schedule ends at 200M tokens, so the 100M point is mid-schedule at about 55% of peak LR and the 100M-to-200M gain includes the annealing gain. A run with a longer schedule would have a smaller gain per token over the same interval. Only a constant-LR or longer-schedule continuation, or re-scoring checkpoints at 100M of a 100M-schedule run, separates data from schedule: not available here.
- 128-sequence val on v1 (41.7% near-duplicate val docs per K9), loss in nats/token, not clean80 bits/char; the gate value is therefore an overestimate for fresh data. n = 3 seeds, sd of the gain across seeds < 0.2 points.
- What can be said: 14M models at 200M tokens (about one epoch of v2, 0.2B tokens) are not data-limited in the sense of a flat curve. Whether a 1.2B model needing ~20B tokens binds on data is not addressed by these logs.
