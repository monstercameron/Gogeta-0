## 2. Critique

Builds on 0837 items 1-10 (bf16 recurrence, ternary as two ingredients, init, log vs ratio scale, LR of the 200M cells, LOSO at n=3). The points below are new unless noted.

**Architecture (code-read)**
1. The loop re-injects e ungated on every pass: `h = h + inject([norm h, norm e])` (model.py:302). All F2 loop cells therefore run the un-fixed loop. The 200M loop penalty may be this injection rather than looping itself. SQ15, SQ268 and SQ329 test it at 20M or at eval only; nothing has been run on the 200M cells.
2. Sliding-window attention is counted as windowed but computed as full. `flops_per_token` counts SWA as min(window, T/2) (model.py:357-358), while `Attention.forward` runs SDPA over a T x T boolean mask (model.py:160). So E1's "0.94x FLOPs" (README table) and any per-FLOP number for a cell with SWA blocks is an analytic count, not the compute the kernel does. This is C12 seen from the accounting side, and the README does not mention it.
3. The RoPE table is built once for max_seq_len = 1024 (model.py:252, 113-114). Any context test beyond 1024 needs a code change first (see I6).

**Method**
4. Two headline claims share one confound. C197 says unique parameters are the lever. The F2 loop factor halves unique parameters (0837 triage: 12.3M for 010 vs 27.9M for 000). So "loops cost 10.6%" and C197 are one dataset read two ways, but the README presents them as separate findings. The 0837 triage agreed the loop sentence "must be read" as sharing at fewer unique parameters, but the README status paragraph still says "loops cost 10.6%" with no qualifier. That wording fix is still owed.
5. F2 has no parameter-matched loop arm. INDEX describes E9 as "same 5 blocks, no weight sharing". That is ambiguous: 4 x 5 unique blocks makes it the param-matched control, while 5 blocks applied once makes it FLOP-matched only. Nothing in the docs says which, and F2 has neither arm. Check the E9 config before any "loops cost" sentence is reused.
6. Forking paths on the 200M interaction. v0.4.104 alone added four post-hoc cuts of I (SQ336, SQ337, SQ338, SQ344), reported next to C202, none registered. C202 is PARTIAL, which helps, but the README sentence "the ingredients' penalties compound" carries none of this. The 200M replicate should pre-register one stratum and one LR rule.
7. The 80% overlap cutoff came after K9 (v0.4.33). The README calls the clean-val metric pre-registered for C5. I could not check from the files I read whether 80% was fixed before the K9 analysis. PREDICTIONS.md should show it. SQ323 (cutoff sensitivity) is the right check and is still an idea.
8. Stage-1 F2 exposure: per-run scores were visible during stage 1 (v0.4.89), and N_final = 221 was set from the stage-1 sigma (v0.4.91). The disclosure is in place. Whether the sample-size decision was influenced is unquantified, and probably minor.
9. The README's headline metric is "quality per bit and per FLOP", but quality is measured only as code bpc. Loss-to-capability is untested (C28 PARTIAL). The only functional numbers are E0 on CPU (CRUXEval-O 8.9%, SQ66).
10. The efficiency pillar has no positive measurement. The only wall-clock result (SQ338) is at 1,024 context, where SWA is dense-masked and costs the same as full attention, and GDN is slower (1.62x). The linear-time claim rests on an analytic count at the context we actually run (item 2).

## 3. Alternative ideas

**I1. Copy deficit as the mechanism of the 200M interaction (CPU, inference).**
- Hypothesis (spec): fused cells lose in-context copying at gaps beyond the 256 window, and that loss interaction has the same sign and rough size as I_bpc. SQ344's pattern (I larger on dup80 than clean50) fits a recall deficit.
- Cheapest test: the 15 200M F2 checkpoints (5 cells x 3 seeds), synthetic repeated 32-token identifier-like spans at gaps 128, 256 and 512, 200 sequences per cell and gap, forward only, then I_copy with the SQ263 seed-blocked estimator. About 10-15 CPU-min with 2 threads per job.
- What changes plans: I_copy within 2x of I_bpc means the reversal is a recall deficit, and the next arm is attention-side anchors (C62; SQ35), not a mixer change. I_copy near 0 or of the opposite sign means it is general modelling, so the numerics checks (SQ339, SQ340) come first.
- Novelty: SQ240 (copy probe) is queued only for E0, E1 and E10 on GPU. The factorial version is not queued.

**I2. Logit lens over the loop passes (CPU, inference).**
- Hypothesis (spec): if loop states refine, a readout of h_k through norm_out and head improves with k up to the trained r and then flattens. If they drift, it worsens from about k = 2. A penalty that is already present at k = 1 is an entry problem, not a looping problem.
- Cheapest test: one forward with hooks on cells 010 and 111 (3 seeds each, 200 clean80 docs), per-pass CE for k = 1 to 12. About 10 CPU-min.
- What changes plans: if 111 is already worse at k = 1, the penalty sits in the shared entry (un-gated inject, model.py:302; ternary inject, C63), and SQ268 moves up. If both cells bottom out at the same k, the coda is the bottleneck and SQ270 is next.
- Novelty: SQ14 reads the coda output, SQ230 is effective rank on E2 (GPU), SQ341 is the L(r) curve through the coda. A per-pass lens on the factorial is not queued. Caveat (spec): the head was trained on coda outputs, so the lens is biased; use it only for relative comparisons.

**I3. Does the bpc penalty appear as a syntax penalty? (CPU, generation).**
- Hypothesis (spec): fused and ternary cells produce a larger share of unclosed or unbalanced completions than their bpc ratio predicts. If so, the bpc table understates the cost of fusion for code use.
- Cheapest test: 20 clean80 prompts cut at line boundaries, 64 greedy tokens, 3 seeds each of cells 000, 100 and 111 (9 models, no cache). Metrics: bracket balance at the end of the completion, and indentation consistency. About 20-30 CPU-min. Caveat (spec): 64 tokens and 20 prompts give low power, so a null is weak.
- What changes plans: an error-share ratio of at least 2x the bpc ratio means a functional proxy must be added before any "fusion is worse by X%" sentence. A match means bpc is a fair stand-in.
- Novelty: SQ4 and SQ60 are functional evals that need downloads (Q14 HUMAN). SQ37 measures repetition, not syntax. SQ300 needs GPU and a repair setup.

**I4. Parameter-matched loop control (GPU, needs approval).**
- Hypothesis (spec): at equal unique parameters, a 7-block core applied twice beats the same core applied once (half the FLOPs) by more than the 10.6% reported for loops, so most of the loop penalty is the unique-parameter deficit.
- Cheapest test: 20M, 2 seeds, three arms: 7 unique blocks x 2 applications, 7 unique blocks x 1 application, and 14 unique x 1 (the F2 layout). About 6 runs at roughly 0.6 min each plus compile, so about 10 GPU-min once approved.
- What changes plans: if loop x2 beats unshared-7 at equal params, loops buy quality per unique parameter, and the README needs a per-parameter cost. If it ties, looping is pure FLOP cost with no parameter saving, and the final-model plan should drop loops from the default.
- Novelty: SQ32 matches params and FLOPs for MixerLoop, SQ266 is a fixed-r sweep, and E9 is unclear (item 5). The 7-block matched-param arm is not queued.

**I5. Power for the 200M replicate (computed, CPU, 1 min).**
- Hypothesis (spec, from 3 values): the seed-level sd of I at 200M is about 2.5 points. From SQ336's per-seed values (8.83, 3.94, 5.86) the sd is 2.46 (computed; df = 2, so the estimate is loose).
- Test: arithmetic only. At 80% power and two-sided alpha 0.05, a paired test needs about 12 seeds to detect a 2-point I and about 3 seeds for a 4-point I (computed, normal approximation; a t-correction adds a few).
- What changes plans: resolving about 2 points needs about 12 seeds per cell, roughly 45 more 200M runs, so GPU approval is required. A 20M replicate is cheaper but answers C201's question, not C202's.
- Novelty: SQ253 is a power simulation for SQ243 only. SQ224 and SQ94 are leave-one-out checks, not power calculations.

**I6. Does GDN extrapolate in length where RoPE attention cannot? (CPU, inference).**
- Hypothesis (spec): the GDN cell (100) keeps its per-token loss from 1,024 to 2,048 tokens, while dense RoPE attention (000) degrades. Then the dense baseline's shortfall at 2k is about RoPE and not about the mixer.
- Cheapest test: 200M cells 000 and 100 (3 seeds each) on clean80 docs longer than 1,200 tokens (C193 says some exist), scored at 2,048 tokens. This needs the RoPE table rebuilt for 2,048 (model.py:113-114, 252) and a plain-PyTorch GDN forward on CPU. About 30-60 CPU-min.
- What changes plans: if GDN's advantage grows past 1,024, the efficiency pillar gets its first positive evidence beyond analytic FLOPs. If not, the pillar is a FLOP argument at this scale and the README should say so. Caveat: this tests extrapolation, not cost; wall-clock still needs a block-sparse kernel (SQ3).
- Novelty: SQ237 (GPU, GDN-only to 4,096), SQ327 (truncation) and SQ244 (wall-clock) are related. The CPU version on the F2 checkpoints is new.

## 4. The one experiment I would run next

**I1, the copy-deficit probe on the 15 200M F2 checkpoints.**
- Why: the only open part of the headline (C202) is its mechanism. The probe uses checkpoints already on disk, runs on CPU, and its result decides the next design step (attention anchors vs numerics checks). SQ344's dup80 pattern is the one stratum-level signal we have, and it points at recall.
- Order (AGENTS §0, §6): commit the prediction and criterion in a tagged PATCH before running. Spec prediction: I_copy at gaps 256 and 512 is positive, its CI excludes 0, and it is within 2x of I_bpc (+6.2).
- Falsifier (spec): |I_copy| below 1 point, or the opposite sign. That moves the mechanism to general modelling.
