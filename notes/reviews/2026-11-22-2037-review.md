## 2. Critique

1. **C193 cannot separate length from corpus.** The length bins use only the 330 out-of-corpus files. Without in-corpus bins on the same length scale, "the gap depends on length" and "the gap depends on corpus × length" are not distinguished. The reviewer's own caveat (file type) stays open. The test that matters is an interaction term (gap ~ corpus × log length) with a cluster bootstrap, not per-bin CIs.
2. **The headline protocol is not the protocol that C193 used.** Training-time val is packed windows, which start mid-document (C101). Most positions in a packed window have long context, so the packed number weights the regime where C193 says E1 loses. C193 is doc-level. Nothing shows the in-corpus E1−E0 sign under doc-level scoring. The protocol choice can flip the sign, and no record shows it was checked.
3. **clean80 is a selected subset, not a random one.** It is defined by removing near-duplicates at an 80%-13-gram threshold, a filter that can correlate with length and template style. Its length distribution is not reported against in-corpus val or the frozen test split (A1). The threshold is arbitrary; clean50 exists but is not used as a sensitivity check on the gap.
4. **The 3.6% headline is about the size of E0's own handicap.** E10 and E0 have identical shapes, FLOPs and LR, yet E10 is 3.7% lower at the same LR (computed from 0.6063 vs the E10 mean). SQ200 is the test of that init explanation, and it is queued behind Phase 2b. [spec] The headline gap may be mostly the baseline's init, not the architecture. Phase 2b, once it runs, is the first test that is not confounded this way.
5. **Precision is a possible confound between arms.** `gogeta/model.py:190` casts GDN inputs to bf16 on CUDA, and the kernel runs in bf16. Nothing in the ledger says E10 (HF Llama) uses the same dtype path. A dtype-matched comparison has not been run.
6. **The LR was tuned at 20M tokens and applied at 200M.** K7 is one seed at 20M, selected on the contaminated val (C92). The optimum's horizon transfer is untested, yet the E1 "1.5% handicap" figure is a 20M estimate used to justify 6e-3 at 200M.
7. **Seed counts cannot carry the claims.** Three seeds give a poor sd estimate, and a 0.6% relative spread is near the effect size of the E1 advantage over E10 (computed above). Byte Quest's E14 prediction ("within ±0.5%") cannot be shown as equivalence with 2–3 seeds at a noise level near 0.6%. It needs a TOST design with the noise floor measured first (SQ216 does this, and should gate E14).
8. **Cloud move (cross-hardware comparability).** compute-rental.md recommends 8× RTX 3090 at about $1.60/hr, with the N1X as local. [spec] If any paired comparison (E10 vs E1, or any Byte Quest arm pair) runs across two GPU classes, hardware is confounded with arm, and fla's autotune and Triton kernel choices can differ by device. The fix: each paired comparison runs on one device class, and a same-config, same-seed bridge run (about 2k steps on each device) measures the drift before results are compared. Hardware is already a ledger scope field, so per-device results can stay separate. The SQ220 pilot is the right first step and should be run before any Phase 2b-style comparison uses the cloud.
9. **Byte Quest X1 still confounds sharing with parameter count** (2007 triage (4) fixed this for A″, but E14 has the same structure: its equal-FLOP unshared decoder has about 2× the parameters of the shared loop). The byte claims need a parameter-matched arm, or the sweep reads as "more parameters" or "recurrence" depending on which way it lands.
10. **README is behind the ledger.** README line 47 still gives the out-of-corpus gap as "+0.4%, CI −0.1% to +1.0%" with no mention of C193. AGENTS §0 says a claim may appear as fact only if it is VERIFIED, and C193 changes how the SQ99 line reads. The version badge also still says v0.4.65 while DEVLOG is at v0.4.69 (AGENTS §1 requires it be bumped with each version).

**What C193 should change about Phase 2b (my view, [spec]):** the registered analysis should keep the three-seed clean80 comparison as primary, but add length-binned gaps (doc-level, token-weighted and equal-source-weighted) as pre-registered secondary outcomes with an interaction test. The report should state which protocol the headline uses. Given item 4 and the 0.2% seed-0 figure above, I expect Phase 2b to show no E1 advantage over tuned E10 on clean80 [spec]. If it does, the C193 length structure decides whether the advantage is limited to short files.

## 3. Alternative ideas (5–6, each new to side-quests.md or the queue unless noted)

- **I1. Protocol swap on existing checkpoints.** [spec] Hypothesis: E1's clean80 advantage over E0 has the opposite sign under doc-level scoring from packed-window scoring. Cheapest test: re-score E0 and E1 seed 0 (and E10 seed 0 when available) on clean80 under both protocols, with length strata and position-in-window bins. Inference only, about 10 min on CPU or a few GPU-min. Changes plans: a sign flip means the Phase 2b headline needs a pre-registered protocol before Q12. Novelty: C101 records the level gap between protocols, and SQ214 bins position, but no item compares the E1−E0 gap across protocols. Partly overlaps SQ214.
- **I2. Dtype-matched E1 vs E10.** [spec] Hypothesis: the bf16 GDN path (model.py:190) shifts the E1−E10 gap by more than 0.3%. Cheapest test: score the same clean80 docs with the GDN path in fp32 and bf16 on the same device (checkpoints exist), plus a 5k-step tiny run if the scoring result is ambiguous. Changes plans: if the shift is above seed noise, every GPU-scored E1 number needs a dtype label, and the cloud bridge (item 8) must include it. Novelty: SQ95 covers scorer parity for E0 only, and the E1 path is not listed.
- **I3. LR-optimum horizon check.** [spec] Hypothesis: the optimal LR at 60M tokens equals the 20M optimum for both E10 and E1. Cheapest test: 2 LRs × 2 models × 60M tokens, one seed each (about 30% of a 200M run each, roughly 40 GPU-min total). Changes plans: if the optimum moves, C92 and every 200M LR (Phase 2b included) is wrong for the horizon. Novelty: SQ201 varies horizon at a fixed LR; this tests the LR optimum across horizon.
- **I4. Character n-gram floor for Byte Quest.** [spec] Hypothesis: a character 5-gram model with Kneser-Ney smoothing, trained on code-py-v1 train and scored on clean80 in bits/char, lands within 15–25% of E0. A byte model that does not clearly beat it has learned little beyond local statistics. Cheapest test: CPU, a few minutes with a counting implementation. Changes plans: sets the floor that E12–E16 must clear before any loop or granularity claim. Novelty: SQ204 is an n-gram copy floor on the near-dup band, a different purpose. No byte-level n-gram floor is listed.
- **I5. Length-indexed copy probe.** [spec] Hypothesis: E0 copies random-token sequences reliably at 512 and 1,024 tokens, while E1 degrades beyond its 256-token window (GDN state aside). That would explain C193's long-document reversal mechanistically. Cheapest test: inference only on synthetic prompts at lengths 128/256/512/1,024, E0 vs E1, about 5 CPU-min. Changes plans: if E1 is at chance beyond 256, long-document loss is a copy failure, and E13/E16 at byte lengths of 1,024+ should expect the same. Novelty: SQ63 and C108 redesign a recall probe, but neither targets length; this one does.
- **I6. Deduplicated-family training.** [spec] Hypothesis: the E1−E0 gap shrinks on the one-doc-per-family training set (A1's v2, 737.6k docs, 214.7M tokens) at matched steps. If it does, the in-corpus advantage is partly template memorisation, the reading SQ99 first proposed and C193 now complicates. Cheapest test: two 20M-token runs per model at K7 scale, about 40 GPU-min total. Changes plans: a disappearing gap points at data, not architecture. Novelty: SQ190 varies repetition by epochs, which is related but a different manipulation. SQ102 (named in the A1 hand-back, v0.4.55) may cover this; I could not find it in side-quests.md, so the overlap is unconfirmed.
