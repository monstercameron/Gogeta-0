## What it will test, in plain English

> **Can the model still learn well if every one of its numbers is only allowed to be −1, 0 or +1?**
>
> A model's "knowledge" lives in millions of numbers (its *parameters*). Normally each one is stored precisely, using 16 bits, like `0.0213` or `−1.7754`. **Ternary** weights (the "BitNet b1.58" idea) allow just three values: **−1, 0 or +1**. Each number then needs only about 1.6 bits instead of 16.
>
> **Why bother?**
> - **Much smaller:** the main body of our best model shrinks from **22 MB to under 3 MB**.
> - **Simpler maths, in principle:** multiplying by −1, 0 or +1 is just subtracting, skipping or adding, which cheap chips, phones and FPGAs could exploit with dedicated ternary kernels. Our code only simulates the rounding in normal floating-point maths, so it runs *slower*, not faster (check K2).
>
> **The catch** is quality. Rounding every number to −1/0/+1 throws information away. Researchers found the loss disappears for **big** models (3 billion parameters and up), but ours has 14 *million*. So the real question is: **how much worse does a tiny model get?**
>
> We'll take our best model so far ([E1](E1.html)) and change **only** this one thing, so any difference is down to ternary weights alone.

## The design: one change from E1

| | [E1](E1.html) (done) | E3 (planned) |
|---|---|---|
| Layers | SWA, GDN, GDN, SWA, GDN, full attention | **identical** |
| Data, tokens, schedule, seed | 200M Python tokens, cosine LR 3e-3, seed 0 | **identical** |
| Projection weights | 16-bit | **ternary (−1, 0, +1) × one scale per layer** |
| Activations fed into those layers | 16-bit | **8-bit** |

**What becomes ternary:** all **33** projection layers inside the blocks: the attention and Gated DeltaNet q/k/v/output projections and gates, and both halves of every MLP. That's **11.06M of 11.09M** non-embedding parameters (99.7%).

**What stays full precision** (as in BitNet): the **word table** (embeddings, 3.15M parameters), the normalisation layers, the tiny Gated DeltaNet decay/strength gates, and the short convolutions. That's 33K numbers outside the word table.

## How ternary weights work

For each layer, every forward pass during training:

1. **Scale:** take the average size of the layer's weights, `s = mean(|W|)`.
2. **Round:** divide every weight by `s`, round to the nearest whole number, and clip to −1, 0 or +1.
3. **Rescale:** multiply back by `s`, so the layer keeps roughly the right overall strength.
4. **Activations:** the numbers flowing *into* the layer are rounded to 8-bit integers, per token.
5. **Learning anyway:** rounding has no useful slope to learn from, so training keeps a hidden full-precision copy of each weight and updates *that*, pretending the rounding wasn't there (the "straight-through estimator"). After training, only the ternary version is needed.

This is all implemented in `gogeta/model.py` (`BitLinear`) and covered by the tests: weights take exactly the values {−1, 0, +1}, and backward passes stay finite.

## The memory payoff

| Weights on disk | 16-bit (E1) | Ternary (E3) | Smaller by |
|---|---|---|---|
| Model body (non-embedding) | 22.2 MB | **2.8 MB** (2-bit packed) | **7.8×** |
| Whole model | 28.5 MB | **9.1 MB** | 3.1× |

Notice the second row: once the body is ternary, the **word table (6.3 MB) becomes two-thirds of the whole model**. At our size, shrinking the embeddings (a smaller vocabulary, or quantising them too) would be the next memory win.

## What the research says

The BitNet b1.58 paper (in our reading list) trained ternary and normal versions of the same models:

| Model size | Normal perplexity | Ternary perplexity | Gap |
|---|---|---|---|
| 700M | 12.33 | 12.87 | +4.4% (≈ +1.7% in loss) |
| 1.3B | 11.25 | 11.29 | +0.4% |
| 3B | 10.04 | 9.91 | ternary slightly *better* |

The gap **shrinks as models grow** and closes around 3B. Our model is roughly **60× smaller than their smallest**, so we expect a clearly bigger gap. Measuring how big is the point of E3.

Their production model (BitNet b1.58 2B4T) also uses tricks we're deliberately **not** using in E3, to keep it a one-change experiment: an extra normalisation inside each layer ("SubLN"), squared-ReLU instead of SwiGLU in the MLP, and a two-stage schedule (a high learning rate, then a sudden cooldown halfway, with weight decay switched off in the second half).

## How we'll judge it

- **Main number:** validation loss vs E1 (0.585), same data and seed.
- **Efficiency:** loss *per megabyte of weights*. A slightly worse model that's 7.8× smaller in its body can still be the better deal.
- **Speed:** tokens/second vs E1. We expect E3 to be *slower* in training, because the rounding is simulated in normal floating-point maths. Real speedups need special ternary kernels, which we don't have yet.

**Decision rules (written before the run):**
- **Gap ≤ 3%:** ternary is nearly free even at 14M. Great news for the full fusion.
- **Gap 3–10%:** the expected zone. Ternary works, at a real but known price.
- **Gap > 10%:** try the BitNet recipe (two-stage schedule, SubLN) as a follow-up before blaming ternary itself.

## Risks and caveats

- **One seed**, like E0–E2. A gap of a few percent needs replication to be trusted.
- **No real speed or memory savings during training:** it's simulated. The savings are real for a stored or exported model, and need custom kernels to show up as speed.
- **Our recipe differs from BitNet's** (see above), on purpose. A poor result might say more about the recipe than about ternary weights.
- **Ternary + loops is a separate question.** Whether rounding errors pile up when the same ternary layers run several times is tested in [E4](E4.html), the full fusion.
