What it means, in plain English

We tried making the model "think in loops" by reusing the same few layers several times. It didn't help yet, and it revealed something interesting about why.

Instead of 6 different layers, E2 has a small block of 3 layers that it runs again and again on the same text, about 4 times on average. The hope: like re-reading your work, each extra pass should improve the answer, and you'd get a "deep" model without storing more parameters.

Result: E2 came out 2% worse than the plain baseline (E0) and 6% worse than E1, while doing about twice as much arithmetic. Looping cost more and bought nothing, at least at this size.

The interesting part: during training we randomly used anywhere from 1 to 7 loops. Afterwards we tested the same model with different loop counts. If each pass improved the answer, more loops should always help. Instead, the model did best at 4 loops, exactly the average it was trained with, and got worse with 8 or 12. It learned "the routine is about 4 passes", not "each pass makes things better". Imagine a student who learned to check their homework exactly four times: checking a fifth time doesn't help, it confuses them.

That's exactly the problem the project's "Rival Loop" idea (E6) was designed to fix, so now it's a measured problem, not a guess.

Prediction (written before the run)

Written 2026-11-22 before the run. At r=4 (about 2x E0's FLOPs/token, 11% fewer non-emb params), val loss matches E0 within +-3%, so we expect no win per token yet; the claim to test is the r curve. Predicted shape: r=1 clearly worse (> +10% vs r=4); r=2 < r=1; r=4 about r=6 (flat); r=8 about the same or slightly better than r=4; r=12 (beyond the trained max of 7) flat or slightly worse, not a collapse. Training is stable (no loss spikes > 0.5 after warmup).

What we tested

The initial FusionDance layout, in full precision (no ternary weights yet):

[sliding window]                        ← prelude, runs once
[Gated DeltaNet, Gated DeltaNet, sliding window] × r   ← the looped core, same weights each pass
[full attention]                        ← coda, runs once
  • During training, the loop count r was picked at random between 1 and 7 for each batch (average 4). To save memory, only the last 4 passes were trained directly.
  • Before each pass, the model's original reading of the text is mixed back in, so it doesn't lose track of the input.
  • 12.6M parameters (9.5M excluding the word table): 11% fewer than E0, but because the core runs ~4 times it behaves like a 14-layer model and costs ~2× E0's compute per token.

Results

Breakdown of the findings

  1. No win yet: 0.619 validation loss at 4 loops, vs 0.606 (E0) and 0.585 (E1). It was the worst of the three at every checkpoint, and never reached E0's final quality at all.
  2. Twice the cost: 3.87e16 training FLOPs (E0: 1.94e16, E1: 1.82e16) and 80 minutes of training (E0: 23).
  3. Fewer parameters, slightly worse: 11% fewer stored parameters than E0 for 2% worse loss. As a pure memory saving that's not a terrible trade, but it doesn't justify the doubled compute.

Extra passes help up to 4, then hurt. Going past the trained range (12 loops) costs 5.7%. A loop that was really "refining an answer" would level off, not get worse.

  1. Stable training: no loss spikes. The largest update size (gradient norm 0.67) was higher than E0/E1's 0.38, but nothing broke.
  2. Samples: solved the palindrome prompt. Its fibonacci had broken control flow, but it wrote the correct test values fibonacci(10) == 55, (20) == 6765, (30) == 832040, facts it memorised from training.

Caveats

  • The fair comparison is still missing. E2 differs from E1 in two ways at once: it shares weights across passes, and it has a different number of layers. E9, the same blocks run once without looping, separates the two. It was started but interrupted at 10% and is on hold.
  • One seed. The seed-1 rerun was interrupted at step 200.
  • Small model, short training. Looping might pay off at larger scale or with longer training. Papers that report wins from looping use much bigger models.

What's next

  1. E9, the unlooped control.
  2. Diagnose why extra loops hurt: measure how the model's internal state changes from pass to pass.
  3. Train the loop to improve on every pass (per-loop supervision, the first step of the "Rival Loop", E6).
