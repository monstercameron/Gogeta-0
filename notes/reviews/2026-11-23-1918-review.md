## 2. Critique

**2.1 R1 is confounded with BPTT truncation (code-read, computed).**
- E27 uses bptt_loops 4 with r ~ U{1..7} (the ModelConfig default loops_max is 7, model.py:52; the E27 config was not opened). Passes with r > 4 run under no_grad (model.py:364-367).
- F-6 (a1g.json: loops_max 3, bptt_loops 4) and A2s (a2s.json: loops 2, bptt_loops 2) never truncate, so they are full backprop.
- Computed: E[max(0, r-4)] over r = 1..7 is (0+0+0+0+1+2+3)/7 = 0.857 skipped backward passes, out of a mean of 4 loops (about 21% of core backward work, rough).
- Quoted compute gap: 3.79e16 (A2s) vs 3.41-3.43e16 (E27) (C209 row). Computed ratio 3.79/3.42 = 1.108, so +11%. That is the same order as the truncation effect above, and the same size as the "shape" effect R1 is meant to price.
- The fix already exists: E27_cm (221.6M tokens, seeds 2-4, FLOP-matched to A2s at 3.78-3.80e16 vs 3.79e16; C209 evidence, v0.5.30). F-6 at 200M has A2s's compute, so F-6 vs E27_cm is the compute-matched R1. Adding it as a second comparator costs zero GPU. It must go into the readout before any F-6 number is read (the PREDICTIONS "freeze the readout" rule).

**2.2 The LR coverage of both arms is one-sided (quoted, computed).**
- A2s's seed-5 bracket was best at its lowest point: clean80 0.27291 / 0.27449 / 0.28367 at 3e-3 / 6e-3 / 1.2e-2 (C209 evidence, a3_assembled.json). 6e-3 is 0.58% worse (computed: 0.27449/0.27291 - 1). The optimum is not bracketed from below, yet the C209 row says policy 2.3 "is met for both arms". That is weaker than the status says.
- C1 uses the same grid on a single seed. If F-6 again peaks at 3e-3, the batch cannot say what happens below it.
- The R2 VERIFIED rule ("within 1% of the bracket's best") rests on one seed. C209's per-seed sd is about 0.48 points (computed from -17.05 / -16.12 / -16.82), so a 1% threshold is about two sd and easily met by chance.
- Fix: add 1.5e-3 on seed 5 (one run, about 11 GPU-min at C1's rate) for both arms, and state that the LR rule is a one-seed check.

**2.3 S is R1 relabelled and has no uncertainty (computed, quoted rule).**
- Because ln(A2s/E27) = ln(F6/E27) + ln(A2s/F6), the two shares sum to 1 by construction. S carries no information beyond R1 and R2.
- Inputs: R1 = -11.6% gives ln(0.884) = -0.1234. C209 = -16.67% gives ln(0.8333) = -0.1823. S = 0.677, matching the registered 0.68.
- The thresholds (0.5 and 1/3) are applied to a point estimate with no CI. Fix: map the paired log-scale CI of R1 through S. That gives S's interval without extra runs.

**2.4 The R1 "prediction" repeats the screen estimate (quoted, computed).**
- R1 = -11.6% is A1g's exploratory result on seeds 0-1, which were the selection seeds. The prediction range (-14% to -9%) was set after that number. A hit is close to a replication of a selected 2-seed estimate, not a test.
- The A1g CI [-12.3, -11.0] implies a half-width of 0.65 points. On 2 seeds (df 1, t = 12.7), that is an SE of about 0.05 points. The C209 SE is about 0.28 points on 3 seeds. A 2-seed SE five times smaller than a 3-seed SE needs checking against the A1 result file before the prediction is treated as informative.

**2.5 Eval depth and provenance are not in the readout (code-read, quoted).**
- A1g and A2s set loops 2 (A1g's loops_max is 3). The readout does not state the eval r for each arm. F-6 trains on r in {1,2,3} and E27 on r in {1..7}. If E27 is scored at a different r than F-6, R1 includes an eval-depth effect.
- E27 seed 2 comes from sq263_runs.json, not from a2_runs.json (the readout's gather function). The readout copies each run's git commit, so check that E27 seeds 2-4 and A2s share a commit and config before reading R1.

**2.6 bf16 beta in the GDN kernel (code-read, computed bound).**
- On CUDA the GDN branch runs in bf16 (model.py:256). Beta is cast with `.to(dtype)` (model.py:264), while g stays fp32. On CPU everything is fp32.
- Computed bound: bf16 spacing for values in [0.5, 1) is 2^-8 = 0.0039, so rounding error on beta is at most about 0.2% absolute (about 0.4% relative at beta = 0.5). This is a bound, not a measured effect.
- It matters for any CPU-scored check of a GPU-trained checkpoint (SQ432 is planned on CPU), and for the "under 0.5%" fixed-beta result in SQ402. The closest existing item is SQ340 (bf16 emulation). I have not read SQ340, so check whether it covers the beta cast.

**What works (brief):** R2 (A2s vs F-6) is the right test of the compensations at matched shape and matched parameters. Pairing by seed, a frozen readout hash, and a rule that can fail are all good practice.
