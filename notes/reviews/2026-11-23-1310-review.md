## 2. Critique: the full-stack integration

**2.1 Two loops, one truncation rule, one init scale.** A byte refinement loop (r_b, 1-4) inside a trunk loop (r = 2 in A2/A3) nests two loops. `n_nograd = r - bptt_loops` is applied per loop (code-read), so with sampled r the trunk's early passes get no gradient from byte-level loss; the trunk only sees the byte loss through its final state. `effective_depth()` reads `cfg.loops` (default 4), not the pass count of the loop being built (code-read). A byte decoder built from the trunk's `cfg` therefore gets the residual init scale of a 4-loop model whatever its own r. That confounds the shared-vs-unshared byte decoder comparison (H-C2F arm b), exactly as SQ308 found for C197. (spec: the size of the effect is unknown.)

**2.2 Ternary leaks into any module built from the same config.** `make_linear` keys on `cfg.ternary` (code-read). `Block` only overrides precision for mixer and FFN (`ternary_mixer`, `ternary_ffn`). A new byte block built with the trunk's `cfg` becomes BitLinear, including the 192-wide local layers that analysis section 5 says to keep bf16. Per-module overrides are needed before X1. Narrow layers with per-token int8 absmax are untested (spec: they may be the worst place for ternary).

**2.3 "All parts" is a narrow ternary.** A3mx's ternary is four core experts. The DEVLOG v0.5.12 table reads "BitNet ternary (core; full-precision ends; mixer/FFN scope under test in A3)", which is accurate only for the FFN experts. A3mx cannot answer D2 ("does ternary buy anything"), because it is nearly full precision by design (Q4 in PREDICTIONS: "most of ternary's cost is designed away"). Its weight-memory benefit is limited to the core experts (computed share not yet taken). Wording risk: "ternary" in the A3 summary would read as more than it is.

**2.4 MoE in the shared core: three failure points.**
- (a) `combine_aux` averages each layer's balance loss over the layer's grad calls (code-read, moe.py 158-161), and the logged per-layer `load` is averaged over all calls (moe.py 167). An expert can collapse at pass 2 while the averaged balance looks fine, and the per-pass routing is discarded before it is logged.
- (b) The router sees h_k, so the same four experts can be routed differently at each pass. That is a per-pass specialisation without unsharing (spec: this may be why MoE helps the loop, and if so the gain is partly a per-pass function, not parameter count). If routing is identical across passes, the gain is just more unique parameters, which is the C197 lever again (the A3m config has 22.2M total vs 15.1M active, computed from DEVLOG v0.5.10).
- (c) At patch level (coarse-to-fine), the router sees 1/P as many tokens per batch, so balance statistics are noisier and top-2 of 4 experts is decided on fewer samples (spec). A byte-side block that calls the blocks without threading `aux` silently drops the balance loss (code-read: `aux` is only collected in `FusionDance.forward`). The `_gather` path also syncs to the host once per call (`tolist`, moe.py 110), which costs more at byte resolution.

**2.5 Self-speculative drafting is trained at one operating point.** A2 and A3 train at fixed r = 2 (code-read: `loops_min = loops_max`). A draft at r = 1 or r_d < r is a function the model never trained. Acceptance will be low unless the model is trained over a range of r or with per-pass loss (SQ5, SQ98's teacher-forced check on E2 covers only E2). Second, the draft shares passes 1..r_d with the verifier, so GDN and SWA caches are reusable, but the coda reads h_{r_d} in the draft and h_r in verify. The coda's KV written during drafting is therefore from a different function and must be rolled back or recomputed. SQ287 and SQ296 already plan this on E2; the A2/A3 case is the one that matters for goal 4. Third, the lossless claim is bf16-sensitive: SQ70's pass criterion tolerates 3e-2 between the recurrent kernel and its reference, and a greedy argmax can flip on a near-tie even when the algorithm is right. "Lossless" must be defined as identical under one kernel path, with a margin test (spec: how many steps are near-ties is unknown).

**2.6 The copy-deficit fix contradicts the design rule.** DEVLOG v0.5.11 names "attention inside the shared core" as the candidate fix for the GDN copy deficit. That is quadratic and is paid r times, which the README's rule "nothing quadratic lives inside the loop" forbids. The cheaper question is whether the single coda attention is used for copy at all. SQ191 (replace the coda attention with SWA) and SQ240 (copy probe at fixed length) exist but do not ask this for the A-cells. I did not verify whether the F2 GDN cells keep the coda attention; if they drop it, the deficit confounds mixer and attention, and if they keep it, the deficit persists despite one full-attention layer.

**2.7 Overclaims in the wording.**
- "The stack is confirmed: the A1 winners add up to -16.7%" (DEVLOG v0.5.10). A2 changes four things at once (A2s vs A2f differs by ternary alone), and the A1 winners were picked on two seeds with a computed 16.7% chance of a false winner (v0.5.3 calibration, per the 12:40 review). P1 was a registered prediction and a hit, but it shows the combination beats the full fusion, not that each part helps. Additivity is untested.
- README heading "The fusion does not stack at 200M" is still stated as fact; C202 is PARTIAL (its own status line says so). The 12:40 review flagged this and it is still there.
- A2f's "competitive with dense per FLOP" rests on n = 3 with no CI in the DEVLOG.

## 3. Ideas to make the parts work together (all (spec) hypotheses)

**I1. Draft acceptance at fixed-r training.** Hypothesis: a model trained at r = 2 gives an r = 1 or r = 3 draft with greedy agreement of at least 70% with the r = 2 verifier, so goal 4 works without retraining. Cheapest test: on the existing A2s seed 2-4 checkpoints (if on disk, not checked), greedy and top-1 agreement of r_d = 1 and 3 drafts with r = 2 on 50-200 clean80 docs, 256 tokens each, inference only, under one kernel path. Would change plans: below 50% means E8 needs sampled-r or per-pass-loss training (A3 amendment, SQ5). Novelty: SQ98 measures this only for E2; no row covers A2/A3 fixed-r.

**I2. Per-pass MoE routing audit.** Hypothesis: MoE rescues the loop only if routing differs across passes (per-pass specialisation). Cheapest test: log per-pass expert load and the pass-to-pass routing agreement in `moe.stats` (no training), run on the A3m/A3mx checkpoints when they land, or on a TINY CPU model. Would change plans: if routing agreement is above 0.9 across passes, the MoE gain is parameter count, and routing claims are dropped; if it is below, per-pass routing becomes a mechanism to test (SQ357 is the explicit-adapter analogue). Novelty: SQ254-259 cover MoE research and starvation; I could not see a row on per-pass routing, but the grep output was partly omitted, so check.

**I3. Init-depth and precision contracts before X1.** Hypothesis: a byte decoder built from the trunk `cfg` has the wrong residual init scale and wrong precision for its width. Cheapest test: a CPU unit test that builds shared (r = 2) and unshared (2x blocks) byte decoders with the real depth passed to `_init_weights`, and checks residual-output std and step-0 loss, plus a per-module ternary override check. Would change plans: an init-scale gap over 10% means the X1 comparison must fix depth explicitly. Novelty: SQ308 covers this for C197's trunk, not the byte decoder.

**I4. Is the coda attention used for copy?** Hypothesis: the single coda attention carries copy-at-distance in the A2/A3 family, so the GDN copy deficit (SQ347) is a missing attention use, not a missing full-attention layer in the loop. Cheapest test: on an A2s checkpoint, zero the coda attention output and rerun the SQ347 copy probe (inference, GPU minutes or CPU on 64 probes). Would change plans: if the deficit does not move, the coda attention is not doing copy, and the fix is a prelude or coda-side mechanism outside the loop, which obeys the rule. Novelty: SQ191 changes the coda for length, not for copy; SQ240 probes copy but not the coda's role.

**I5. Ternary-scope audit with a fully ternary arm.** Hypothesis: the D2 question needs a model where ternary covers mixers, FFNs and the core, or the wording "ternary" must say "ternary experts". Cheapest test: `param_counts()` on A2f, A2s, A3m, A3x, A3y, A3mx (CPU, seconds), reporting the share of non-embedding params in ternary modules; then register one fully ternary arm (`ternary_fp_ends: false`, mixers and FFN ternary, MoE core) at the same seeds. Would change plans: if A3mx's ternary share is under half, the README's ternary wording must be narrowed. Novelty: SQ339 and SQ365 test ternary costs, not the scope of the A3 arms.

**I6. Lossless-decoding margin test.** Hypothesis: under bf16 the draft/verify numerics flip greedy tokens often enough that "lossless" must be stated per kernel path. Cheapest test: on an A2s checkpoint, record the top-1 logit margin at each greedy step and the max logit difference between the chunk-prefill and recurrent-step paths on the same prefix; count steps where the margin is below that difference (inference only, minutes). Would change plans: a fraction above 1% of steps means the lossless test (SQ287-style) must be run in fp32, or the claim is rewritten. Novelty: SQ287 tests logits and rejection sampling but not the margin; SQ70 covers the kernel error, not the decoding consequence.

## 4. The one experiment I would run next

**I1 (draft acceptance at fixed-r training), on the existing A2s checkpoints, with I6's margin count logged in the same pass.** It is inference only, costs minutes, and decides the integration question that the rest depends on: does a model trained at one loop count give a usable self-draft? If agreement is at least 70%, the fixed-r recipe (A2/A3) can carry goal 4 and E8 needs no retraining. If it is below 50%, E8 must come with sampled-r training, which changes the A3 recipe and the byte refinement design (its per-pass loss). Overlap check first: SQ98 (E2 only). Cost: 50-200 docs x 256 tokens per checkpoint.
